## Admission and compatibility

The bug is in decoded-message admission, not a native transport failure. The Python pump must keep processing command ACKs even when the application pauses receive. Awaiting the 64-slot data queue in that pump, or in the shared process reader, would deadlock bidirectional consumers.

The helper advertises optional `websocket_receive_window_v1`. A compatible Python adapter opts each socket in with `receive_backpressure: true`. Omitted fields default to false. The old required capability set and protocol version remain unchanged. Old helpers receive neither the field nor the new command. Legacy clients retain legacy behavior with new helpers.

For opted-in sockets, Rust owns two FIFO queues. One holds at most 64 pending events. The other holds byte charges for at most 64 emitted but unconsumed data messages. Python sends one receipt after taking each data message from its decoded queue, not when the IPC reader or pump receives it. A receipt releases one oldest charge. No extra receipt task is spawned. Unexpected receipts fail the exchange. Runtime receipt dispatch uses a separate bounded 64-slot channel and never waits on the 32-slot send-command channel.

The socket owner stops reads when pending events reach 64. It still selects receipts, commands and cancellation through its existing task owner. Control frames can progress while pending space remains. A control frame behind 64 pending messages cannot be read without admitting preceding data, so it waits for consumption. This is deliberate bounded TCP backpressure, not a claim that controls bypass arbitrary unread data. No reader/writer split task or unbounded channel is added.

## Payload and residual bounds

The 32 MiB receive budget sums retained native pending payload charges and charges for unconsumed forwarded data. Text charges UTF-8 bytes. Interpreted Responses text charges original text, raw JSON payload and routing metadata. Binary charges base64 and decoded bytes. Byte excess emits a non-retryable `consumer_backpressure` error for only the affected exchange. It does not increase the Python decoded queue, the existing 4096-event/32 MiB IPC queue, or the existing 16 MiB upstream message limit.

This is a payload-admission bound, not a whole-process RSS bound. A socket read may temporarily materialize one additional message before its charge is checked. At the existing 16 MiB message limit, that rejected event can include a text copy or base64 representation, plus bounded Responses interpretation metadata. Responses interpretation already has its own 1 MiB limit. Serialization, pipe buffers, queue nodes, and JSON/Python object overhead are outside payload accounting. There are at most 128 admitted events per socket across the pending and forwarded window, plus one current read/serialization operation. The shared IPC queue retains its independent original bound. Kernel TCP buffers and the WebSocket library's receive buffers remain transport-owned, not an unbounded application backlog.

## Terminal ownership

Peer close flushes the wire acknowledgement immediately, releases the closed transport independently of application credits, and disables keepalive timers, then queues the close behind already-admitted data. In the pinned tokio-tungstenite implementation, flush writes the close reply but does not shut down TCP; retaining that transport while waiting for credits can deadlock a peer awaiting transport shutdown before the application drains. The bounded receive-window owner therefore outlives the transport. Sends after peer transport retirement fail only their command with the existing error envelope (`websocket_send` phase), preserving the ordered receive data and terminal event. The close event waits for a decoded slot but earns no data receipt. Explicit local close or cancellation may retire unread data and must not report ordinary item fullness as byte overflow. Stdin EOF aborts socket owners and joins their tasks. No retry, cross-account, quota, replay or Python service policy changes are included.

## Qualification boundary

Retained baseline evidence uses the real predecessor helper and public native and `/v1` HTTP bridge. Candidate evidence must use a newly compiled debug helper from the current Rust files and record its digest. Test-only observation hooks pause application consumption, not native socket reads, and use real loopback origins. Final preparation requires whole relevant modules and whole Rust workspace tests, fmt, clippy, static/type/architecture and strict OpenSpec checks. Parent full-tier composition and a final composed native rebuild remain separate gates.
